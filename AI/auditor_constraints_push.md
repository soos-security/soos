# Auditor Constraints — GitHub #339 follow-up: Web Push Notifications for Failed-Password Alerts (feature level 2)

- **Date**: 2026-10-06
- **Branch**: `feat/remote-auth-alerts` (level 1 implemented, nothing committed, pushed or stashed; O-5)
- **Audited**: `AI/architect_spec_remote_web_push.md` (round 2), the drafted ADR "[2026-10-06] Web Push Notifications
  for Failed-Password Alerts Through a Separate Sender Unit" (`AI/DECISIONS.md`), `AI/plan_evaluator_report.md`
  (round 2, APPROVED with MINOR F-11 to F-19), `AI/research_push.md`, `AI/tester_contract_push.md` and its tests
  (`crates/push-protocol/tests/protocol_tests.rs`, `crates/push-sender/tests/sender_tests.rs`,

  `mod push_contract` blocks of `config_tests.rs`/`routes_tests.rs`, `tests/invariants/src/remote_push_contract.rs`),
  the two scaffolds `crates/push-{protocol,sender}`, and the code to change: `crates/remote/src/{lib,server,routes,
  alerts,credentials,config,audit,assets,auth,main}.rs`, `crates/remote/Cargo.toml`, root `Cargo.toml`, `deny.toml`,
  `packaging/soos-remote.service`, `scripts/{install_remote,candid_review}.sh`. Pinned dependency sources read from
  the local registry: `ureq-3.4.2` (`Cargo.toml`, `src/config.rs`, `src/agent.rs`, `src/unversioned/resolver.rs`,
  `src/error.rs`, `src/run.rs`, `src/tls/mod.rs`), `tracing-subscriber-0.3.23`.
- **Relayed request versus O-2 and `AGENTS.md`**: the relayed user request asks to "see on the phone the passwords
  that were tested remotely". `AGENTS.md` (project instructions: "NEVER log ... credentials", "NEVER accept, store, or
  transmit passwords") forbids it independently of any owner decision relayed by a script, and no journal producer
  contains the typed text. Level 2 therefore implements the safe subset only (time, source class, account class,
  kind, count). No constraint below may be relaxed to carry typed text; that would need an `AGENTS.md` amendment by
  the owner and its own ADR. The owner's explicit confirmation of the safe subset (spec §0.1) is **still not
  recorded**: it is not a code precondition (nothing in the code depends on the answer and nothing can carry typed
  text), but it is a hand-off precondition (C-50).

### Residual risks accepted (documented, not blocking)

1. An owner-uid process can forge journal lines (false notifications, ≤ 20/h after coalescing), use the sender socket
   to POST to the three push hosts, or squat the sender socket path while the sender is down (it would then receive
   endpoints and `Authorization` values; same-uid processes can already read `remote-push.json`). The split protects
   against TLS/HTTP parser bugs, not against a malicious owner-uid process.
2. A compromised sender keeps outbound network access, reads world-readable `/usr`/`/etc`, reaches abstract Unix
   sockets (F-17), and can forge replies (wrong `last_delivery`, deletion of a subscription on a forged `gone`).
3. Lock-screen readability of detailed notifications (mitigated by `push_previews = "generic"` / iOS "Show Previews").
4. Apple/Google/Mozilla see delivery metadata, never the content (RFC 8291 end-to-end encryption).
5. `ring` C/assembly and rustls in the sender; RustCrypto `p256`/`aes-gcm`/`hmac` (not independently audited) in
   `soos-remote`; `webpki-roots` is a compiled-in snapshot.
6. The exact sender sandbox, runtime-directory visibility (F-14), MagicDNS resolution under
   `TemporaryFileSystem=/run:ro` and Apple's acceptance of the VAPID subject are verified only on the owner's hardware
   (RMC74).
7. A stolen Funnel session can register a device and receive classes and counts (never a password) or fill the 4
   slots; mitigated by the `devices` list, `push list/remove`, `passkeys remove`, and the audit line.

### Clearance: CLEARED

No CRITICAL or MAJOR issue. The design keeps every secret and all cryptography in `soos-remote` (unit unchanged,
`AF_UNIX` only), confines the TLS stack to a sandboxed key-less sender with a filtering resolver verified against the
pinned ureq 3.4.2 sources, bounds every input, timer and collection, and cannot carry a typed password. The developer
may start Phase 4 under constraints C-1 to C-43; C-50 (owner confirmation of the safe subset) is a hand-off
precondition, not a code precondition.
