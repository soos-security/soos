### Supply-chain Review

**Trust change (the core of this PR).**
- **Default build (unchanged).** `ort-sys` downloads a **pyke-built** static archive of ONNX Runtime 1.28.0 from `cdn.pyke.io` (`build/download/dist.tsv`, e.g. `https://cdn.pyke.io/0/pyke:ort-rs/ms@1.28.0/...`). Its SHA-256 is pinned in `dist.tsv`, which is itself bound by the `ort-sys` crate checksum in `Cargo.lock`. It is not a Microsoft-published binary: the spec's phrase "SHA-256-pinned Microsoft binary" is imprecise (C26). This gives a reproducible, hash-pinned artifact, with trust placed in pyke's build infrastructure and crates.io.
- **System build (new, opt-in).** It trusts the Arch `[extra]` package `onnxruntime-cpu 1.29.0-3`. That package is "Validated By: SHA-256 Sum Signature", packaged by an Arch developer key (`gromit@archlinux.org`) and verified by pacman (`SigLevel = Required DatabaseOptional`) against the `archlinux-keyring` in the digest-pinned image. Its runtime dependencies are `cpuinfo r843.ea6b9f1-1` (an unreleased upstream git snapshot, `[extra]`, signed) and `protobuf 36.1-1` (`[extra]`, signed; it pulls `abseil-cpp`, `zlib`). The version floats with the rolling release, so the build is not reproducible. That risk is accepted (m-8) and the harness prints the version. At run time, the dynamic loader resolves `libonnxruntime.so.1` from `/usr/lib` at every daemon start, so the library becomes part of the root daemon's TCB. Only root or the package manager can replace it.
- **Build-time selection is gated.** `ort-sys` links the system library only through `pkg_config::probe("libonnxruntime")`, with a minor-version ≥ `ORT_API_VERSION` (17) gate. If the probe fails, it falls back to `ORT_LIB_PATH`/`ORT_LIB_LOCATION`, and the harness asserts both are unset. Otherwise it emits `link_error_generic`, so the link fails closed and nothing is downloaded: the download module is not compiled without `download-binaries`. `ort-sys` prints only `rustc-link-search`/`rustc-link-lib` from pkg-config, with no `rustc-link-arg`, so a `.pc` file cannot inject an rpath. C21 still asserts this on the artifact.
- **Mixed link hazard (m-4).** With both features, pkg-config prints its link directives before `ort-sys` rejects an older library. `LIBONNXRUNTIME_NO_PKG_CONFIG=1` (checked first by `pkg-config 0.3.34`) neutralises this in CI and `save.sh` (C17).

**Container image (`tests/docker/Dockerfile.system-ort`).**
- The base image is pinned by digest, identical to `Dockerfile.arch`.
- `pacman -Syu` against the official mirrors verifies the signature of every package. The draft contains no `SigLevel` edit, no AUR, no `-U <url>` and no local key signing.
- If the base image grows old enough for the keyring to go stale, the job fails closed (signature error). It is never bypassed.
- Rust is installed only through `scripts/install_rustup.sh`: the rustup 1.29.1 `rustup-init` is SHA-256 pinned, and the toolchain components are verified by rustup against the HTTPS channel manifest (pre-existing practice, see §2).
- `ARG SOOS_MSRV` has no default.

**Harness and CI network model.** There are three containers, and the repository is mounted `:ro` in all of them:
1. `docker build` uses the network and runs only pacman and rustup.
2. The fetch container uses the network and runs only `cargo fetch --locked` (crates.io checksums from `Cargo.lock`, no build scripts executed) and `scripts/download_models.sh`. That script is HTTPS-only, TLS ≥ 1.2, bounded by `--max-filesize`, and checks SHA-256 per `models/manifest.toml`. The daemon re-verifies the models through `ModelRegistry::verify_integrity`.
3. The build/test container runs with `--network none`, an explicit `-e` environment and the models volume `:ro`.

Every build script and test therefore runs with no network. The job injects no secrets, and none are available (`contents: read`, `persist-credentials: false`).

## Pre-existing Violations Found (not introduced by this change)

1. **Spec drift on the default artifact's origin.** Spec §8/§9 and the issue call the default download a "SHA-256-pinned Microsoft binary". It is a pyke-built archive served from `cdn.pyke.io` (`ort-sys-2.0.0-rc.13/build/download/dist.tsv`). The fix belongs in the ADR wording (C26). The code is unaffected.
2. **Rust toolchain verification in every sandbox image.** `scripts/install_rustup.sh` pins `rustup-init` by SHA-256, but toolchain components are verified only by rustup against the HTTPS channel manifest (no GPG signature check). This is shared by `Dockerfile.arch`, the Fedora/Ubuntu images and the new image. Accepted practice; not changed here.
3. **Arch images upgrade with `pacman -Syu` without refreshing `archlinux-keyring` first** (`Dockerfile.arch`, now also `Dockerfile.system-ort`). As the pinned digest ages, a key rotation can fail the build. This fails closed (signature error), so it is a reliability issue, not a security one.
4. **`--in-container` modes of other harnesses have no container-marker guard** (`tests/docker/network_lock_pkcheck_test.sh`; `authselect_profile_test.sh` checks root only). C22 adds the guard for the new harness only, because it is the only one that removes a package.

That is fail closed, and is noted for the ADR.
6. **`AGENTS.md` lists only 3 `forbid(unsafe_code)` crates** (known drift, project-facts §1). The authoritative list is the invariant.
