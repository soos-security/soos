### Header-trust argument (audited)

The question for this revision is whether reading `X-Forwarded-Host` instead of `Host` opens a path by which a request **without** Serve's headers passes the host check more weakly than under D5a. It does not:

1. **No `X-Forwarded-Host` ⇒ D5a unchanged, plus one stricter rule.** The `Host`-only branch keeps the exact D5a algorithm (`single_header("host")`, OWS, lowercase, one `:443`, `is_valid_host_name`, `*.ts.net`/allowlist). The only addition is that an `X-Forwarded-Proto`, if present, must be exactly one `https`; absent is accepted. Every direct local client (tests, `curl --unix-socket`) therefore sees a check that is identical or stricter than before, never weaker.
2. **`X-Forwarded-Host` present ⇒ the value is a Serve-controlled fact, like `Tailscale-User-Login`.** The socket is `0600` in a `0700` directory; the only writers are `tailscaled` (root) and the owner. The §13.1 probe on the owner's host showed Serve **overwriting** a forged `X-Forwarded-Host`, `X-Forwarded-Proto` and `Tailscale-User-Login` with the real values, which is the same property D3 already relies on for the identity header. A request that reaches the socket with a client-chosen `X-Forwarded-Host` is therefore a request written by the owner on their own socket, which is no escalation (the owner can already read every response). `X-Forwarded-For` is sent by Serve but never read, so no claim is needed about it.
3. **Ignoring `Host` when `X-Forwarded-Host` is present removes no protection.** Behind Serve, `Host` is the fixed backend name (`localhost` in §13.1), chosen by the proxy, not by the phone or by a rebinding page; comparing it to the allowlist can only produce a constant result. Pinning `Host: localhost` would couple the check to a Go `ReverseProxy` detail and would turn into a denial of service, never into a bypass, if it changed; D5a′ correctly does not pin it. The DNS-rebinding defence moves intact to the name the phone actually typed (`X-Forwarded-Host`), which is also what the browser puts into `Origin`, so the lock CSRF comparison (`check_lock_csrf` against the **returned** normalised host) is now meaningful behind Serve (`Origin: https://localhost` → `403`, pinned end to end).
4. **Mandatory `https` with `X-Forwarded-Host` closes the `--http` gap fail-closed.** Whether a plain-HTTP Serve omits `X-Forwarded-Proto` or sends `http`, both are `NotAllowed` (`421`); two identical `https` are `NotAllowed` as well, so a first-/last-header-wins lookup cannot pass. The contract pins all three variants in the pure test and the first two end to end.
5. **Residual, documented, not a weakening.** A future Serve release that stops sending `X-Forwarded-Host` makes every proxied request `421` (fail-closed), never `200`; the spec's §8 residual bullet states exactly this.
