## 1. Context & Objectives

PR 1 (#372, walkthrough 200) made `scripts/setup.sh` install the face profile and deferred the user phase (ADR 2026-10-13 item (9)). The owner wants the one command to set up everything at once (decision of 2026-10-12), and on 2026-10-15 decided, on #400: no VPN on the phone, so Funnel, remote unlock, the camera view and the camera view over Funnel are written on by default together with password alerts, push and offline alerts; each can be turned off later in soos-gui; an explicit `false` already in `remote.toml` is kept unless its `--<feature> on` option is given; the Tailscale login and node name come from `--tailscale-login` / `--rp-id` or a prompt, never from `tailscale status`. The PR 1 scope contract SET3 banned the words this phase needs; the owner approved its migration, applied by the lead in commit 40b0fb1 before this work started.

## 2. Architect Design

Spec `AI/architect_spec_setup_user_phase.md` (§1–§9, Revision 1 §10, Revision 2 §11):

- **Where it runs**: after the root half returned 0 (or 3), in the user half, as the session owner. Skipped with the reason (root start, another `--user`, no `XDG_RUNTIME_DIR`, relative `XDG_CONFIG_HOME`, symbolic link, foreign or writable `~/.config/soos`, no identity); any companion option in such a case is exit 2 before any change.
- **`remote.toml`**: absent → created; the untouched `install_remote.sh` template → replaced; a file carrying setup's marker line and strict grammar → rewritten only when its render differs; any other file → never edited. 0600, `mktemp` + `mv`, 0600 backup `remote.toml.soos-setup.bak`.
- **Features**: seven boolean keys in prerequisite order; option, else kept `false` of a managed file, else on; a key whose prerequisite is off is off; an `on` whose prerequisite is off is exit 2.
- **Install, validate, start**: `scripts/install_remote.sh` every run (its `-p` build differs from the workspace build, so the restart decision rests on checksums of the installed files before and after); `soos-remote --config <file> passkeys list` validates the whole file (78/1 refuse); `systemctl --user enable --now` only for a configuration written for the first time (and the sender when push is switched on); both units active after a 2 s settle (`Type=exec`).
- **Camera view, daemon side**: only when `--sysconfdir` is `/etc` (the daemon reads only `/etc/soos/daemon.toml`), the root half receives `--camera-view on`, creates `daemon.toml` with only the `[preview]` section when the file is absent (0644, hard link), restarts the daemon and waits; an existing file is never edited.
- **Tailscale**: still only `tailscale version` runs; `tailscale funnel` / `serve`, the Funnel node attribute, the 1.102.4 minimum, the passkey enrollment, notifications and the resolver drop-in are printed.
- **Exit 5**: companion failed, its changes rolled back, face install kept.
- **`install_remote.sh`**: copies from `${CARGO_TARGET_DIR:-<checkout>/target}/release`.

ADR: "[2026-10-15] Setup User Phase: Phone Companion Profile With Default-On Features", which amends items (7)–(9) of the #372 ADR and records the SET3 migration.

## 7. Candid Review

Two earlier fresh reviews returned APPROVED with MINOR findings, all fixed before the final review: the companion skip reason is repeated after the run, the exit-5 message names a kept `daemon.toml`, other TOML headers end the `[preview]` scan, a unit the run started is stopped by the rollback (`test_set_u22_rollback_stops_a_unit_started_by_the_run`), exit 78 (configuration) and 1 (passkey store) are reported apart, `~/.config` must be owned by the user, an idle sender left enabled after push was switched off is reported with its disable command, a unit the run restarted is restarted again on the restored file, a configuration directory the failed run created is removed, and an unreadable `remote.toml` is refused before any change. The final review is run by a fresh sub-agent on the final diff (`./scripts/candid_subagent.sh --prepare`); the fingerprint-bound verdict is `AI/candid_review_report.md`, and the branch is pushed only with an APPROVED report that matches the pushed diff (pre-push hook and CI re-check it).

**Lead review of PR #402.** soos-daemon reads only `/etc/soos/daemon.toml`, while the step wrote `<sysconfdir>/soos/daemon.toml`: with a non-default `--sysconfdir` the `[preview]` section would have gone where the daemon never reads it and been reported done. The step now writes and reports done only for `/etc/soos/daemon.toml`; otherwise it prints the change and reports `manual (not applied)` (spec §12, R3-1). Because the contract runs against a fake `--sysconfdir`, four assertions written earlier in this PR changed: `test_set_u5` (plan line `manual (not applied)` instead of `will run`), `test_set_u6` (no `--camera-view on`, no `daemon.toml`, no restart, the change printed instead of the created file), `test_set_u7` (the daemon side is no longer in the "already done" list), `test_set_u14` part 2 (`manual (not applied)` instead of `already done`); `test_set_u16` was rewritten as `test_set_u16_daemon_side_never_written_outside_etc` (the failure path it covered can only run on `/etc`, SET39). A backup path that is not a regular file is now refused (`test_set_u23`). PR 1's `presence.disable` has the same `--sysconfdir` mismatch; reported, not changed.

**Owner decision of 2026-10-17: the root path as real root in Docker.** After the lead review, the `/etc/soos/daemon.toml` creation path (create only when absent, 0644 hard link, `systemctl restart soos-daemon`, readiness gate, removal with exit 1 or 70, no companion after either) was no longer reached by any automated test, since the contract runs against a fake `--sysconfdir`. The owner asked for a Docker test running `setup.sh` as real root before merging (spec §13, R4-1). `tests/docker/setup_root_preview_test.sh` (CI job `setup-root-preview`, required like `systemd-unit` and `network-lock-polkit`, which also run pinned images deterministically; only the Arch `system-onnxruntime` job, which depends on live `[extra]` state, is advisory):

- **Harness choice.** A real `systemctl restart` of the shipped unit needs systemd as PID 1, so the harness reuses the pinned systemd image of the `systemd-unit` job (`tests/docker/Dockerfile.systemd`) with the same host isolation guards (privileged container, masked host-state units asserted, host `kernel.*`/`vm.*`/`fs.*` sysctls compared). The daemon itself is a Python stand-in run by the unchanged `packaging/soos-daemon.service` (`Type=notify`, full sandbox): it binds `/run/soos/daemon.sock`, sends `READY=1`, answers "healthy" to a stand-in `soos-admin status`, and records each start with whether `/etc/soos/daemon.toml` existed; a mode file under `/var/lib/soos-setup-test` makes it refuse to start or report unhealthy while the file exists, or stay down. The readiness gate is the real `scripts/wait_daemon_ready.sh`. No face pipeline, model or camera is used. Building the real daemon would add a release build and model downloads without reaching the failure cases, whose trigger is the daemon's behaviour with the file.
- **What runs for real.** The unmodified `setup.sh` (copied byte for byte into a fake checkout, `cmp`-checked) runs as an unprivileged user with `--yes --skip-packages --no-enroll --camera-view on` and the companion identity, and escalates with the real `sudo` (environment reset, `secure_path`) into `--system-phase` with the default `/etc`. Stubs: `install.sh` (the face install is not under test), `install_remote.sh` (real contract: never root, installs two binaries and two user units), the build user's `cargo`, and `systemctl --user` in the user half's `PATH` only (there is no user manager in the container); the root half uses the real `systemctl`. `setup.sh` has no test hook and gets none: no option, environment variable or path override.
- **Cases.** A1 absent: created with exactly the `[preview]` content (spelled out in the harness, uid of the test account), 0644 root:root, one link, no `.daemon.toml.*` left, `/etc/soos` created 0755; new invocation id and the last start saw the file; `[DONE] camera view (daemon)`; companion ran; exit 0. A2 second run: `already done`, same inode and bytes, same invocation. B an administrator file (0640, fixed mtime): bytes, inode, mode, owner and mtime unchanged, the exact change printed, no restart. C1 the daemon starts but reports unhealthy with the file (the readiness gate times out after 30 s) and is healthy without it: file removed, the `/etc/soos` the run created removed again, exit 1, companion never ran. C2 the restart itself fails with the file: the same, with an existing `/etc/soos` kept. D the daemon never starts: file removed, exit 70, companion never ran. E1/E2 a dangling symbolic link or one to a file: refused and printed, link kept, its target never created or edited, no restart.
- **Red, then green.** The current `setup.sh` passes every case, so each case was run against a deliberately broken copy of `setup.sh` (applied in the working tree for the run, reverted, never committed). Every mutation failed its case: mode 0600 (A1 mode check); `systemctl is-active` instead of the first restart (A1 "not restarted"); `done` state misread as `manual` (A2); existing file treated as absent and replaced with `mv -f` (B: no SKIP line); existing file appended to while the SKIP line is printed (B: "inode, mode, owner, links or mtime changed"); no removal after the failed restart (C1, C2: exit 70 instead of 1); companion allowed after exit 1 (C2: "the phone companion ran after a failed system phase"); `PREVIEW_DAEMON_DOWN` never set (D: exit 1 instead of 70); no symbolic-link state (E1: exit 1; E2: no SKIP line); a write through the link while printing the SKIP line (E1: "the dangling link target was created"; E2: "the link target was edited"); the readiness gate skipped after the restart (C1: the verify phase then fails, exit 70). `test_set_u24_root_preview_docker_job_wired_into_ci` failed (`CI job setup-root-preview`) before the job existed.

## 9. Known Limitations / Follow-ups

- Owner to confirm: AS-U1 a root start skips the companion; AS-U2 an existing `daemon.toml` is never edited (until the TOML editor and `soos-daemon --check-config`); AS-U3 a user-written `remote.toml` is never edited; AS-U4 exit 5; AS-U5 a unit that is not enabled on a re-run stays disabled (also after `install_remote.sh --uninstall`); the journal group for password alerts is reported, never added; `loginctl enable-linger` is printed, never run.
- A key forced off by a prerequisite is written `false` and then kept like a GUI choice until its own `on`.
- A setup-created `daemon.toml` survives `--camera-view off` and `uninstall.sh`.
- On hosts whose `/etc/resolv.conf` points into `/run`, push needs the resolver drop-in (printed, never added).
- The first companion run compiles a second variant of the companion crates (memory peak).
- SET39: the owner's real run on the Arch host (Funnel step, passkey, test push, second run without restart). The Docker test covers the root path with a stand-in daemon on Ubuntu; the real daemon loading the `[preview]` section, on Arch, with a real user manager for the companion, stays this row.
