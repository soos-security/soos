## 2. How the Correction Pass Works (process that proved reliable)

1. One topic branch per issue (`fix/<name>` from `origin/main`), executed by a sub-agent in an isolated worktree following the `dev-workflow` phases (spec → tests first with red evidence → audit → implementation → full gate → traceability: matrix rows, Docs, walkthrough `NN`).
2. Independent candid review per branch (`./scripts/candid_subagent.sh --prepare`, report bound to the diff fingerprint), one rework round if `CHANGES_REQUESTED`.
3. When branches overlap (almost always `AI/VERIFICATION_MATRIX.md`, `AI/DECISIONS.md`, `tests/invariants/src/lib.rs`, `crates/daemon/src/dispatcher.rs`), integrate them on one batch branch with `git -c merge.conflictStyle=diff3 merge --no-ff`; Markdown/test appends are unions, code conflicts are resolved by hand. Then full gate + Docker (`./run_tests.sh`, `tests/docker/authselect_profile_test.sh`) in a scratch clone (the container writes root-owned files into `target/`), one candid review of the integrated diff, one PR whose body carries one `Closes #N` per issue, then `./save.sh --auto-merge`.
4. Any change after a review (even a one-line CI fix) invalidates the fingerprint: re-review before pushing.
