# Architectural Decision Records (ADR) Register

This file records immutable technical decisions to ensure consistency and prevent architectural drift or hallucination across development sessions. All decisions derive strictly from `ARCHITECTURE.md`.

## Active Decisions

* **[2026-09-12] IPC (Inter-Process Communication):** Exclusively use local Unix Domain Sockets (`SOCK_SEQPACKET` or framed `SOCK_STREAM`) with strict `SO_PEERCRED` kernel validation. Zero network sockets.
* **[2026-09-12] PAM Module (`pam_soos.so`):** Must **never** start an asynchronous runtime (Tokio). Exclusively use blocking standard library primitives (`std::os::unix::net::UnixStream`) with a strict 200–250ms timeout. *(Superseded in part by ADR 2026-09-30 "PAM Deadline Derived From Clamped `timeout_ms`": the fixed 200–250 ms figure is no longer the rule; the blocking-only, no-Tokio rule stands.)*
* **[2026-09-12] Panic Safety:** The PAM module catches all panics via `catch_unwind`. In any error or panic condition, it systematically returns `PAM_IGNORE` to silently fall back to password authentication.
* **[2026-09-12] Camera & Hardware Access:** The root daemon is the exclusive owner of the `/dev/video*` capture device. Use the `v4l` crate (not `nokhwa`) to utilize kernel MMAP buffers in production.
* **[2026-09-12] Artificial Intelligence Engine:** Use `ort` (ONNX Runtime) in CPU execution mode. Importing or linking OpenCV is strictly forbidden.
* **[2026-09-13] Project Naming:** The project is named `soos`. The PAM shared object is `pam_soos.so`, the privileged background process is `soos-daemon`. Legacy references to "ZTLH" or "pam_ztlh" are deprecated.
* **[2026-09-13] Codec & Framing:** Use `postcard` + `serde` for IPC payload serialization. JSON is forbidden. Maximum payload size is capped at 4,096 bytes with big-endian length prefix.
* **[2026-09-13] Commit Standard & Language:** Conventional Commits 1.0.0 is strictly enforced across the repository via `.githooks/commit-msg`. All codebase deliverables (code, docs, PRs, commits, walkthroughs) are authored in 100% English.
* **[2026-09-16] Production Hardening & Memory Hygiene:** Decrypted embeddings, biometric templates, and raw frames enforce `Zeroize` / `ZeroizeOnDrop`. Sensitive key and embedding allocations are protected against swap paging via best-effort kernel `mlock` page pinning. Cargo-deny blocks duplicate dependencies (`multiple-versions = "deny"`), security advisories, and non-permissive licenses.
* **[2026-09-20] Next-Generation AI Models:** The 4-model pipeline (UltraFace Slim 320 + landmark_5point + MobileFaceNet 128D + MiniFASNet) is replaced by a 3-model pipeline: **SCRFD 500M KPS** (unified face detection + 5-point landmarks, ~2.4MB, MIT), **ArcFace MobileFaceNet w600k** (512D embeddings, ~3.6MB, MIT), and **MiniFASNetV2** (80×80 anti-spoofing, ~1.8MB, Apache-2.0). SCRFD eliminates the separate landmark model, saving ~20ms latency. *(The embedding model description is corrected by the 2026-09-30 "Face Embedding Model Identity" entry below: the attested file is an ArcFace ResNet34, not a MobileFaceNet.)*
* **[2026-09-20] SCRFD Detection Architecture:** SCRFD uses multi-stride (8/16/32) distance-to-border box decoding with grid-based anchors, replacing UltraFace's center-offset prior-based decoding. Input is BGR 640×640 with letterbox padding. Output tensors are parsed by ordinal grouping (3 per stride: score, bbox, kps). *(Superseded by the 2026-09-30 "Single-Source Vision Thresholds and Letterbox" entry: outputs are matched by shape, not ordinal.)*
* **[2026-09-20] Embedding Dimensionality:** Biometric embeddings are upgraded from 128D to 512D. Normalization denominator changes from 128.0 to 127.5 for exact symmetric [-1.0, +1.0] range. No migration required (development state, no enrolled users).
* **[2026-09-20] PAD Crop Strategy:** MiniFASNetV2 receives a 2.7× expanded bounding box crop (80×80, BGR, pixel/255.0 normalization) instead of the aligned 112×112 crop. This provides wider context for anti-spoofing analysis. PAD and embedding use different crops from the same detection.
* **[2026-09-20] MiniFASNetV2 Class Ordering:** The QingHeYang ONNX fork uses `[Live, Print, Replay]` ordering (Class 0 = Live). The `OrtPadDetector` constructor accepts a configurable `live_class_index` parameter defaulting to 0, with a startup validation test against known fixtures. *(Superseded by the 2026-09-29 entry below.)*
* **[2026-09-29] Release Panic Strategy = `unwind` (supersedes the `panic = "abort"` choice recorded in walkthrough 11):** The shipped `pam_soos.so` is built by `[profile.release]` in every packaging path (`scripts/build_*.sh`, `packaging/**`, Docker matrix). Under `panic = "abort"` every `catch_unwind` in the module is a no-op, so the Panic Safety decision above was not honored by the installed artifact: a panic (including an overflow trapped by `overflow-checks = true`) killed the PAM host (gdm, sudo, login, screen locker) instead of degrading to `PAM_IGNORE` (review finding PAM-01 / TCI-01, GitHub #148, reproduced in Docker: `pam_test_runner` aborted with exit 134). Rust cannot select the panic strategy per package, so the whole workspace release profile is `panic = "unwind"`; abort semantics are not retained elsewhere because Rust already aborts when a panic escapes an `extern "C"` function (the defense-in-depth `abort` used to provide at the FFI boundary), and a Tokio daemon benefits from task-level panic isolation. The value is pinned by `tests/invariants` and proven on the release-built artifact by Docker case T10 through the opt-in, never-packaged `fault-injection` feature of `soos-pam`.
* **[2026-09-29] MiniFASNetV2 Live Class Index — Single Source of Truth (supersedes the 2026-09-20 "Class Ordering" entry):** The shipped `minifasnet_v2_80x80.onnx` is interpreted with the upstream Silent-Face-Anti-Spoofing class order `[PrintPhoto, Live, ScreenReplay]`, i.e. **live class index 1** (upstream `test.py`: `label == 1` is a real face), as established by the screen-replay bypass analysis of walkthrough 72. The value is defined exactly once, as `DEFAULT_MINIFASNET_LIVE_CLASS_INDEX` in `crates/inference-ort/src/pad.rs`; `soos-daemon`, `soos-enroll` and `soos-gui` construct the detector with `OrtPadDetector::new` and never pass an index (`new_with_class_index` / `with_live_class_index` are test-only, enforced by the repository invariant `test_no_pad_live_class_index_override_outside_tests`). The 2026-09-20 statement (live class first, default index zero) is obsolete, and the literal `2` that walkthrough 66 left in the daemon and the enrollment CLI was a security defect (GitHub #146: screen replays scored as live on the PAM path). An empirical re-measurement on real captures with the real model is tracked by PAD-06 (GitHub #172); any change of the index must go through this constant and a new ADR entry.
* **[2026-09-30] MiniFASNetV2 Class-Order Contract — One Canonical Statement (GitHub #171, PAD-05; refines the 2026-09-29 entry above):** The contract is stated in exactly one form everywhere: MiniFASNetV2 class order `[PrintPhoto, Live, ScreenReplay]`, **live class index 1**, value owned by `DEFAULT_MINIFASNET_LIVE_CLASS_INDEX` in `crates/inference-ort/src/pad.rs`. The code constant is the truth; prose follows it. The repository invariant `pad_contract::test_minifasnet_class_contract_prose_matches_code_constant` parses the constant and scans every living document (`AGENTS.md`, `AI/ARCHITECTURE.md`, `AI/DECISIONS.md`, `AI/VERIFICATION_MATRIX.md`, `AI/BACKLOG.md`, `models/README.md`, `Docs/**`, `.agents/skills/**`) for live-class-index claims (`live class index N`, `DEFAULT_MINIFASNET_LIVE_CLASS_INDEX = N`, `Class N = Live`, three-class orderings); any disagreement fails the build. A historical statement kept for the record must carry the explicit marker `*(Superseded ...)*` on the same line; numbered walkthroughs and dated review reports are immutable history and are not scanned. `pad_contract::test_pad_matrix_rows_cite_existing_tests` additionally requires the PAD matrix rows (PAD1, NGM9, NGM10, ASG1, ASG2, PLC1–PLC3, PTF1) to cite only tests that exist. The empirical re-verification of the index on real captures remains open under PAD-06 (GitHub #172).
* **[2026-09-30] Operator Threshold Security Floor (GitHub #170, PAD-04):** Thresholds from `[pipeline.thresholds]` in `daemon.toml` are built with `ThresholdConfigBuilder::build_with_security_floor()`, never with the unvalidated `ThresholdConfig::new_raw`. Besides NaN / infinity / `[0.0, 1.0]`, it refuses `match_threshold < ThresholdConfig::MIN_MATCH_THRESHOLD = 0.40` and `pad_threshold < ThresholdConfig::MIN_PAD_THRESHOLD = 0.50`; `soos-daemon` then fails to start with `DaemonError::Config` naming the setting. Rationale: `pad_threshold = 0` (a plausible typo or "make it work" edit) classified every frame as live and disabled anti-spoofing silently — fail-open by configuration. No `unsafe_thresholds` override flag is provided: an operator who wants biometrics off uses `/etc/soos/disabled`, which falls back to the password (`PAM_IGNORE`) instead of weakening the check. The policy builder's plain `build()` keeps its domain-only contract for library and test callers; the invariant `pad_contract::test_thresholds_never_built_unvalidated_outside_policy` forbids `new_raw(` in production code outside `soos-policy`.
* **[2026-09-29] Multi-Frame PAD Consensus (GitHub #147):** The daemon never authorizes on a single capture. `Allow` requires `DEFAULT_PAD_CONSENSUS_REQUIRED = 3` consecutive distinct captures that are live at or above `pad_threshold` and match at or above `match_threshold`, inside a bounded window of `DEFAULT_PAD_CONSENSUS_WINDOW = 5` captures (`soos_policy::PadAggregator`, zero I/O). Any capture classified as a spoof (or with a non-finite liveness score) vetoes `Allow` for the entire request, and the veto cannot be reset within a request. The per-UID rate limiter records exactly one attempt per request; a rate-limit rejection at recording time downgrades `Allow` to `ProtocolError`/`RateLimited`.
* **[2026-09-30] Format-Aware PAD and Short-Term IR Liveness Policy (GitHub #169, review finding PAD-03):** MiniFASNetV2 is RGB-trained, while `CameraConfig::default()` prefers the IR sensor (`SensorPreference::PreferIr`) and `convert_to_rgb` replicates a `Grey` byte into three identical channels, so IR captures are out-of-distribution for the model. The vision pipeline derives `PadInputModality` from `frame.format` (`Grey` => `Monochrome`, every other format => `Color`) and a monochrome frame never takes the colour PAD path: (1) a fail-closed IR gate on the 80×80 PAD crop (`soos_vision::evaluate_ir_gate`: mean luma in `[20, 235]`, luma std-dev `>= 10`, texture energy `>= 2`) rejects unlit, saturated, flat or texture-less crops with `VisionError::IrLivenessGateFailed` before the model is consulted (NIR physics: LCD/OLED screens emit almost no 850/940 nm light, and a missing emitter yields an unlit crop); (2) the model score must reach `max(pad_threshold, ir_pad_threshold)` with `DEFAULT_IR_PAD_THRESHOLD = 0.95`, never looser than the colour threshold, and NaN scores or thresholds always reject. The daemon maps a gate failure to a spoof capture (request veto, `Deny`/`PadFailed`, password fallback). All of these values are **conservative and uncalibrated**: they are sanity bounds, not measurements, and no FAR/FRR figure is claimed for IR. `soos` does not drive the IR emitter (requirements in `Docs/CAMERA_V4L_CRATE.md`). Follow-ups requiring hardware: IR calibration on captured frames (GitHub #172 / PAD-06), then either PAD on the RGB sibling sensor while matching on IR, or an IR-trained PAD model; IR nodes that deliver a colour pixel format (e.g. YUYV) are classified by format only and remain on the colour path until a sensor-type flag is carried by `Frame`.
* **[2026-09-29] Camera Preview Stream Exception (GitHub #143, CAM-01 / DMN-02):** `RequestKind::PreviewFrame` is the only channel through which camera frames may leave `soos-daemon`, exclusively towards the diagnostic GUI. The dispatcher serves it only after kernel `SO_PEERCRED` verification and: (a) the peer is root, or (b) `[preview] enabled = true` **and** the peer UID is listed in `[preview] allowed_uids` **and** `peer_uid == uid_hint` **and** the peer owns an active logind session. The section is absent/disabled by default (fail-closed), the allow-list is bounded to 64 UIDs, every preview request is rate limited per peer UID (default 40 per second, root included), refusals are standard `Response` messages (`ProtocolError`) with zero pixel bytes, and preview buffers are zeroized on drop. Frames never transit through the PAM module.
* **[2026-09-30] Single Camera Resolver & GUI Camera Ownership (GitHub #150, #152, CAM-02 / CAM-04):** `soos-daemon`, `soos-enroll` and `soos-gui` resolve the camera exclusively through `soos_camera_v4l::resolve_camera_device`: explicit path verbatim, otherwise the capture node matching `sensor_preference` (default `PreferIr`) through its `/dev/v4l/by-id/` alias, otherwise the `/dev/v4l/by-id/default-camera` sentinel. `""`, `auto` and `default` are sentinels everywhere. The daemon no longer silently replaces an explicit `camera_device` that is absent at startup (it was the only binary doing so). `soos-gui` opens `/dev/video*` directly only when the daemon is provably not running (socket `ENOENT`/`ECONNREFUSED` and `soos-daemon.service` inactive); in every other case it uses the daemon preview or shows a blocked notice, never a silent direct fallback.
* **[2026-09-30] Local Session Binding for Facial `Auth` (GitHub #160, review finding DMN-09):** Face verification is granted only when the request originates from a local, active, seat-attached logind session of the target user; the policy lives in `crates/daemon/src/session_policy.rs` (`LocalSessionPolicy`) behind the mockable `LogindSource` trait and runs as dispatcher Step 6b for every `RequestKind::Auth`. (1) **Root peer** (`su`, `sudo`, `sshd`, display-manager workers, polkit helper): the request is tied to the caller's own session, resolved from the kernel `SO_PEERCRED` PID through `/proc/<pid>/cgroup` (`session-<id>.scope`, the mapping `sd_pid_get_session` uses; a process cannot move itself into another user's root-owned session scope). That session record must have `UID` equal to the target, `ACTIVE=1`/`STATE=active`, `REMOTE=0` (explicit), a non-empty `SEAT=` and `CLASS=user`. This refuses `su B` / `sudo -u` flows started from user A's session (local or SSH) while B sits in front of the camera, `sudo` from any SSH session, and `sshd` logins (sshd is in no session). (2) **Unprivileged peer**: `SO_PEERCRED` already proves `peer.uid == uid_hint` (no identity crossing), and the target must own at least one active session not flagged `REMOTE=1`; a remote-only user cannot light the camera. (3) **Fail closed**: missing or non-positive peer PID, a PID outside any session scope, a vanished session, an unreadable sessions directory, a malformed session ID, an oversized cgroup file (16 KiB bound) or more than 1024 session entries all deny with `ProtocolError`/`UidMismatch`, so PAM returns `PAM_IGNORE` and the password prompt follows; there is no path from a lookup error to `Allow`. `enforce_active_session = false` disables the policy (test harnesses only). The preview path keeps `SessionValidator`, which now also ignores `REMOTE=1` sessions. **Accepted consequences**: the initial GDM/TTY login (target has no session yet, caller is not in a target session) never uses face, as before this change; lock screens depend on the PAM worker living in the user's session scope or user manager (to be confirmed on hardware for GDM reauthentication, `swaylock`, KDE). **Amendment (user decision 2026-09-30, candid review finding 1)**: GNOME ≥ 3.34 and KDE Plasma ≥ 5.25 run terminal emulators (`app.slice/app-org.gnome.Terminal.slice/vte-spawn-*.scope`, `app-org.kde.konsole-*.scope`) and the shell's polkit agent (`session.slice/org.gnome.Shell@wayland.service`) under the systemd user manager, not in a `session-<id>.scope`, so the original rule refused face `sudo`/polkit on every modern desktop. A root peer whose cgroup resolves to no session scope is therefore **also** allowed when (a) its cgroup (unified `0::` and/or v1 `name=systemd` lines, all agreeing) is `/user.slice/user-<uid>.slice/user@<uid>.service/<child>...` with both `<uid>` parsed strictly (ASCII decimal, no sign, no leading zero, fits `u32`, slice and service equal) and equal to the target UID; (b) the target owns at least one session meeting the record criteria above (active, `REMOTE=0`, seat, `CLASS=user`); and (c) the target owns no session flagged `REMOTE=1` or with an unknown remote flag, in any state (a record without `UID=` counts as possibly the target's), because an SSH session of the same account, including a closing one with a lingering `tmux`, could reach the user manager through `systemd-run --user sudo ...` and obtain root through the face of the person at the desk. `/user.slice` and `user-<uid>.slice` are root-owned, so a process cannot move itself under another user's manager; `su B` from A's terminal runs in `user@A.service` and is refused (`user_manager_uid_mismatch`). Denials use distinct codes (`user_manager_cgroup_malformed`, `user_manager_uid_mismatch`, `user_manager_caller_remote_session_active`, `user_manager_no_local_seat_session`); every parse or IO error denies. Session-scope resolution was tightened at the same time to the `sd_pid_get_session` rule (only the first unit below the slices counts), so a user-named `session-<id>.scope` nested inside a user manager is never taken for a logind session; the session-scope record rules are unchanged, and so is the unprivileged-peer rule. **Residual risk accepted with the amendment**: malware already running as the target user inside the desktop session (under the user manager) can invoke `sudo` and have it granted by the face of the legitimate user sitting at the desk; this is inherent to face `sudo` (the same holds for a terminal in the session scope) and is equivalent to the password case where the user types the password into a compromised session. **Residual risks**: SO_PEERCRED PIDs are subject to reuse between `connect(2)` and the cgroup read (the PAM host blocks on the reply, so the window is narrow; `SO_PEERPIDFD` is a follow-up), and a future `ProtectProc=invisible` hardening (review DMN-14) would hide `/proc/<pid>` of other users from the daemon and make every root-peer request fail closed, so that hardening must keep the daemon able to read `/proc/<pid>/cgroup`.
* **[2026-09-30] Per-Peer Connection Admission (GitHub #157, review finding DMN-04):** The daemon admits connections through `soos_daemon::limits::PeerConnectionLimiter`, keyed on the kernel `SO_PEERCRED` UID read once before any byte of the stream, instead of a single global semaphore acquired before the peer was known. Of `[dispatcher] max_concurrent_connections` (default 8), `reserved_root_connections` (default 2) are usable only by root peers, because the PAM module runs inside root processes (gdm-session-worker, sudo, su, login, polkit-agent-helper-1); each unprivileged UID holds at most `max_connections_per_uid` (default 2) connections; root is exempt from the per-UID cap but still bounded by the capacity. A refused peer is logged with `peer_uid` and its stream is closed immediately (EOF => `PAM_IGNORE` on the PAM side), never queued. An admitted connection serves at most `max_requests_per_connection` (1024) requests, is not read again after `max_connection_lifetime` (30 s), and an `Auth` request is one-shot (closed after its response). Values come from `[peer_limits]` in `daemon.toml`; a reservation that is not strictly below the capacity, or any zero bound, fails startup. Rationale: a single `soos`-group account opening 8 idle-polling connections denied face login to every user indefinitely.
* **[2026-09-30] PasswordFailed Event Trust Model (GitHub #175, review findings PAM-04 / DMN-03):** The only legitimate emitter of `EventKind::PasswordFailed` is `pam_soos.so event=password-failed`, which runs in the process calling `pam_authenticate`. `SO_PEERCRED` reports that process's effective UID at `connect(2)`: `0` for sudo, su, login, gdm-session-worker and polkit-agent-helper-1 (root or setuid root), and the session user's own UID for screen lockers that authenticate their own user (swaylock, i3lock, ...). The GDM greeter user never runs the PAM stack of the user logging in. Rule (enforced in `ConnectionDispatcher::handle_event` before the event quota): an event is accepted only when `peer_uid == 0` or `event.uid` is `None` or `Some(peer_uid)`; the target is `event.uid.unwrap_or(peer_uid)`; any other event is dropped with a `warn` naming `peer_uid` and the claimed UID, and no snapshot is taken. Accepted events are then counted against the per-peer-UID quota `[peer_limits] max_events_per_window` / `event_window_ms` (default 5 per 10 s, root included). Contract migration: the setup of `pipeline_integration_tests::test_12_4_password_failed_event_captures_evidence_snapshot` used an unprivileged test peer reporting for `current_uid + 42`, which encoded the vulnerable behaviour; with explicit user approval (2026-09-30) its target UID became the peer's own UID, assertions unchanged (walkthrough 95).
* **[2026-09-30] GDM PAM Stack Placement (GitHub #177 / #180, review findings STO-03 / STO-07):** `soos-admin gdm enable` writes `GDM_PAM_LINE` = `auth  [success=done default=ignore]  pam_soos.so timeout_ms=2500` (no `service=`: the module reads `PAM_SERVICE`, which drives `gdm.disable`). The explicit control replaces `sufficient` for consistency with every packaged soos rule (`packaging/pam/*`); Linux-PAM defines `sufficient` as `[success=done new_authtok_reqd=done default=ignore]`, so behavior is unchanged: `done` never overrides an already-failed `required` rule, and any non-success return (including `PAM_IGNORE`, errors and an uninstalled module) is ignored. Placement rules: (1) a face success must never skip a lockout, nologin, shell or user-filter gate, so the rule is inserted immediately before the **anchor**, the first `auth` rule that is a delegation (`include`, `substack`, `@include`) or one of the documented credential modules `CREDENTIAL_MODULES` = `pam_unix.so`, `pam_sss.so`, `pam_ldap.so`, `pam_krb5.so`, `pam_winbind.so`, `pam_systemd_home.so`, `pam_fprintd.so` (modules that verify a password, directory/Kerberos secret, systemd-homed secret or fingerprint; `pam_gnome_keyring.so` is not a credential gate and is not on the list); the only rules allowed before the anchor are the pre-credential allow-list (`pam_access`, `pam_env`, `pam_faildelay`, `pam_faillock preauth`, `pam_listfile`, `pam_nologin`, `pam_securetty`, `pam_selinux_permit`, `pam_shells`, `pam_succeed_if`), after which soos goes, so it is never at index 0 in front of anything else; **any other (unclassified) auth rule before the anchor makes `enable` refuse with an error naming the rule and write nothing** (no backup, file unchanged, `gdm.disable` kept), because soos cannot tell whether an unknown module (`pam_tally2`, `pam_group`, a vendor module) is a lockout or login gate; (2) when that anchor delegates, the gates the delegated stack runs before its first credential module (`pam_faillock.so preauth`, `pam_nologin.so`, `pam_shells.so`, `pam_succeed_if.so`, `pam_access.so`, `pam_listfile.so`, `pam_securetty.so` with a plain `required`/`requisite` control) are copied in front of `pam_soos.so`, following includes up to `MAX_PAM_INCLUDE_DEPTH` = 4; if the delegated stack ends without a credential module the rules after the delegation in the edited file are scanned the same way; `pam_env`/`pam_faildelay` are skipped; any other rule met before the credential module (an unclassified module, a conditional (jump) or `sufficient`/`optional` gate that cannot be copied without changing its meaning), an include target not resolvable inside the PAM directory (absolute path, a file missing from the directory, or any read error) and a stack that reaches no credential module at all make `enable` refuse; rules after the credential module are never copied; an administrator resolves a refusal by removing/migrating the rule or by writing the `pam_soos.so` rule by hand, which `enable` never touches (`Docs/DISTRIBUTION_DEPLOYMENT.md` §2.1) (rework of candid review 2026-09-30 Finding 1: the anchor was previously "the first rule not on the pre-credential allow-list", which placed soos before an unknown lockout module or skipped copying a delegated `faillock preauth`); (3) the account phase is never edited, because GDM runs `pam_acct_mgmt` after `pam_authenticate`, so account-phase `pam_nologin`/`pam_faillock`/`pam_unix` always apply; (4) the inserted rules live between `GDM_BLOCK_BEGIN`/`GDM_BLOCK_END` markers, which makes `enable` idempotent and lets it migrate the pre-#177 `LEGACY_GDM_PAM_LINE`; an administrator-written `pam_soos.so` rule is never touched; (5) fail closed without modification when there is no anchor, a `[...=N]` jump would change target, the file is not UTF-8, uses continuations, exceeds 64 KiB, is a symlink, or `pam_soos.so` is not installed (binary check over `DEFAULT_PAM_MODULE_DIRS` or `--pam-module-dir`); (6) `gdm restore` atomically returns the `.soos-backup` bytes and removes the backup; the backup is type- and size-checked and read through one `O_NOFOLLOW` descriptor. (7) as in libpam (`pam.conf(5)`), the type and control keywords (`auth`, `include`, `substack`, `required`, `requisite`, `optional`, `sufficient`, bracketed `key=value` controls) are parsed case-insensitively for gate classification, delegation detection and jump detection; module paths and arguments stay case-sensitive; (8) a delegated gate is dropped as a duplicate only when an earlier `auth` rule of the edited file runs the same module and arguments with a plain `required`/`requisite` control (an `optional` copy does not enforce anything) (rework of candid review round 2, Findings 2 and 3). Consequences: fail-closed refusals are expected on stacks that run unclassified modules before the credential module, notably the Fedora/RHEL/Alma/Rocky authselect `sssd` profile (`pam_usertype`, `pam_localuser` before `pam_unix`) and openSUSE `common-auth` (`optional pam_gnome_keyring` before `pam_unix`); only the directory of the edited file is searched, never a vendor directory such as openSUSE `/usr/lib/pam.d`, so vendor-directory stacks are refused and need the manual rule (`Docs/DISTRIBUTION_DEPLOYMENT.md` §2.1 item 6); (9) a delegated target missing from the PAM directory, or failing to read, makes `enable` refuse (no write, no backup, `gdm.disable` kept): libpam may load it from a vendor directory, or install a must-fail handler that a `success=done` soos rule would bypass (rework of candid review round 2 Finding 1; it was previously treated as "nothing to guard"). Test migration approved by the user on 2026-09-30: the pre-existing `gdm_tests` contracts that enable `@include common-auth` (`test_gdm_disable_and_enable_lifecycle`, `test_gdm_enable_creates_byte_exact_backup_with_original_mode`, `test_gdm_enable_never_overwrites_an_existing_backup`, `test_gdm_enable_is_atomic_and_idempotent`) now write a `common-auth` fixture (`auth required pam_unix.so`) in their setup, with no assertion changed, except one explicitly approved change: the expected directory listing of `test_gdm_enable_is_atomic_and_idempotent` now includes `common-auth`. Supersedes the implicit "before `@include common-auth`, else first line" behavior (walkthroughs 72/73, 91). Walkthrough 98.
* **[2026-09-30] Biometric Template Erasure Model (GitHub #179, review finding STO-06):** The guarantee that a discarded biometric template cannot be recovered is **encryption at rest plus master-key destruction (crypto-erasure)**, not block overwriting. Every template is AES-256-GCM ciphertext under `/var/lib/soos/master.key`; any residual copy (stale blocks, journal, snapshot, backup, SSD spare area) is undecryptable without that key, and destroying the key erases every template written under it. That destruction is itself only as strong as the storage of the 32-byte key file, so hosts requiring a hard guarantee keep `/var/lib/soos` on full-disk encryption. In addition, `BiometricStore` overwrites a template inode in place before releasing it, as **best-effort defense in depth**: `delete` overwrites (3 CSPRNG passes, `fsync` each), unlinks and syncs the directory; `enroll` replacing an existing template retains a handle on the old inode (regular file, `O_NOFOLLOW | O_NONBLOCK`, inode re-checked), commits the new template by temporary file + `fsync` + atomic rename + directory `fsync`, then overwrites the old inode through the handle (the replace stays atomic; an overwrite failure is reported as an error after the commit). In-place overwrite is documented as ineffective on copy-on-write filesystems (btrfs, ZFS), data journaling, snapshots/backups and wear-levelled flash media; no document, CLI or GUI message may claim that deleted templates are "unrecoverable" or "securely shredded". `BiometricTemplate::to_cbor` returns its plaintext in a pre-reserved `Zeroizing<Vec<u8>>`. A per-template data key stored in the template file was rejected: deleting that key and deleting the file are the same operation on the same blocks, and a separate key store only moves the problem.
